# MILESTONES — בדיחה בלחיצה

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md` (והתמונות `wireframes.png`, `style-guide.png`, `mockups.png`).

## עקרונות מנחים

- הפיתוח מיועד למסך מובייל אחד בלבד, בעברית וב-RTL, ללא תפריט או מסכים נוספים.
- מימוש לפי ה-Technology Stack שנבחר: React, TypeScript, Vite, CSS, Vercel Function, OpenAI Responses API במודל `gpt-5`, ו-`vite-plugin-pwa`.
- אין Database, Authentication, שמירת היסטוריה או Rate Limiting של המוצר.
- כל Milestone מסתיים בתוצר שניתן להריץ ולבדוק. רכיבי תשתית המוקמים לפני חיבור ה-AI לא יוצגו למשתמש כיכולת שכבר עובדת.
- ה-PRD גובר על רכיבים דקורטיביים סותרים בתמונות; בפרט אין לממש את אייקון התפריט שמופיע בחלק מה-Mockups.
- **מ-Milestone 1 ואילך, כל דחיפה מאושרת ל-`main` מתפרסמת אוטומטית ל-Production** (ARCHITECTURE, ‏ADR-1). בדיקות בטלפון לפני אישור נעשות על Preview ידני (ADR-2).
- פעולות בחשבונות (Vercel, OpenAI) מבצע בעל המוצר בעצמו, בהדרכה צעד אחר צעד.

## Milestone 1 — הקמת פרויקט, מסך ראשי וחיבור ל-Vercel ✅

**שם ומטרה:** לבסס אפליקציית מובייל ניתנת להרצה עם המסך היחיד ועיצובו, ולחבר את הפרויקט ל-Vercel כבר עכשיו — לפני חיבור לשירות ה-AI.

**דרישות מקדימות:** הקובץ `spec/assets/kitten.png` סופק (DESIGN 1.5).

**מה יש לממש:**
- יצירת פרויקט React + TypeScript עם Vite, תשתית CSS, וגופני Heebo ו-Assistant כחלק מהפרויקט (`@fontsource`).
- מימוש מסך **"בדיחה בלחיצה"** בהתאם למבנה ה-Wireframes ולעיצוב ה-Style Guide וה-Mockups: אזור כותרת עם תמונת החתלתול, שדה נושא עם מונה תווים, לחצן **"צור בדיחה"**, וכותרת "הבדיחה שלך" עם כרטיס הבדיחה במצב הריק. כל הטקסטים לפי טבלת הטקסטים (DESIGN 1.3).
- ממשק RTL בעברית, צבעי המותג (כולל Raspberry לכפתור), טיפוגרפיה, רכיבים מעוגלים ופריסת עמודה אחת.
- שדה נושא אופציונלי המוגבל ל-100 תווים; טקסט מודבק ארוך נחתך ל-100; המונה מתעדכן.
- הגדרת תצוגת טקסט אזור הבדיחה כך שתתמוך גם בתוכן LTR ובתוכן ארוך, ללא גלילה אופקית.
- עד לחיבור השירות, **הכפתור מוצג כמושבת** (בשקיפות 50%) ואין להציג בדיחות שמתחזות לתוצאה של GPT-5.
- הדרכת בעל המוצר בפתיחת חשבון Vercel, התקנת Vercel CLI, קישור הפרויקט (`vercel link`) וחיבור ה-Repository ב-GitHub לפרויקט ב-Vercel.
- יצירת Preview ידני (`vercel deploy`, באישור בעל המוצר) כדי לבדוק את המסך בטלפון.

**תוצר מצופה:** מסך מעוצב ותקין שרץ מקומית ובכתובת Preview; ניתן להזין ולערוך נושא, אך טרם ניתן להפיק בדיחה. אחרי אישור ודחיפה — המסך מתפרסם ב-Production.

**Definition of Done:**
- הפרויקט מותקן, נבנה ללא שגיאות TypeScript ונטען מקומית.
- כל הרכיבים המרכזיים מופיעים במסך יחיד, בפריסה הדומה למקורות העיצוב וללא תפריט ניווט; כל הטקסטים תואמים לטבלה ב-DESIGN 1.3.
- הממשק בעברית ו-RTL; הזנת 100 תווים מתאפשרת, תו 101 אינו מתקבל, והדבקה של טקסט ארוך נחתכת ל-100.
- תצוגת המובייל אינה גורמת לגלילה אופקית, וניתן לבדוק בה טקסט ארוך בשלב הפיתוח.
- הפרויקט מקושר ל-Vercel, וכתובת ה-Preview נפתחת בטלפון ומציגה את המסך.
- אין מפתחות API או סודות בקוד הלקוח או ב-Repository.

## Milestone 2 — יצירת בדיחה מקצה לקצה ✅

**שם ומטרה:** לספק את ה-Vertical Slice המרכזי: הזנת נושא, יצירת בדיחה חדשה ב-GPT-5 והצגתה באותו מסך — כולל טעינה ושגיאות בסיסיות, כדי שלא יהיה מצב ביניים לא תקין.

**דרישות מקדימות (בעל המוצר, בהדרכה):** פרויקט ב-OpenAI עם **תקרת הוצאה חודשית קשיחה** ועם התראות; מפתח פיתוח ומפתח Production; הגדרת המפתחות ב-Vercel (פיתוח ל-Preview, Production ל-Production) ומילוי המפתח המקומי ב-`.env`.

**מה יש לממש:**
- Vercel Function ב-TypeScript עבור `POST /api/joke`, כולל אימות קלט בצד השרת, טיפול בנושאים ריקים/רווחים והחזרת JSON לפי חוזה ה-API שב-ARCHITECTURE (כולל `405`, `413` ו-`504`).
- שימוש ב-OpenAI SDK וב-Responses API עם המודל `gpt-5`, ברמת חשיבה מינימלית, עם `max_output_tokens: 800` ו-Timeout של 30 שניות (ADR-3).
- הוראות למודל לפי כללי השפה (PRD FR-02) ומדיניות התוכן (PRD FR-07); ללא סגנון או אורך קשיחים.
- `.env.example` עם שם המשתנה `OPENAI_API_KEY` בלבד; המפתח המקומי ב-`.env`. הרצה מקומית באמצעות `vercel dev`.
- חיבור הכפתור ל-`/api/joke` באמצעות בקשה חדשה בכל לחיצה, והחלפת הטקסט בכרטיס הבדיחה ללא שמירת היסטוריה.
- מצב **טעינה** ("מכין לך בדיחה..." בכרטיס, כפתור מושבת) ומצב **שגיאה** (הודעה מתחת לכפתור, הבדיחה הקודמת חוזרת) לפי DESIGN 1.4.
- תצוגת בדיחה כ-Plain Text בכיווניות המתאימה לשפת התוצאה.
- בדיקות אוטומטיות (Vitest) לאימות הקלט ב-API: נושא ריק, רווחים בלבד, 100 תווים (תקין), 101 תווים (נדחה), JSON לא תקין ושיטה שאינה `POST`. עדכון פקודת הבדיקות ב-`CLAUDE.md`.

**תוצר מצופה:** משתמש יכול להזין נושא או להשאיר את השדה ריק, ללחוץ על הכפתור ולקבל בדיחה אמיתית שנוצרה ב-GPT-5, עם חיווי טעינה והודעה ברורה בכשל.

**Definition of Done:**
- בדיחה בנושא בעברית מוצגת בעברית; נושא שהוא משפט באנגלית מפיק בדיחה באנגלית; שם מותג בודד בלועזית (למשל "iPhone") מפיק בדיחה בעברית; שדה ריק או רווחים בלבד מפיקים בדיחה כללית בעברית.
- נושא לא מתאים מפיק בדיחה כללית מתאימה לכל המשפחה, ללא הודעת סירוב.
- שתי לחיצות עוקבות לאחר השלמת הבקשה מפעילות שתי בקשות יצירה נפרדות, והבדיחה החדשה מחליפה את הקודמת בכרטיס הקיים (ללא הבטחה ששתי תוצאות המודל תהיינה שונות).
- בזמן טעינה הכפתור מושבת ולא ניתן לשלוח בקשה נוספת; בכשל מוצגת הודעת השגיאה והכפתור חוזר להיות פעיל.
- בדיחה טיפוסית מתקבלת תוך שניות ספורות.
- API דוחה קלט שאינו תקין, לרבות נושא ארוך מ-100 תווים, גם אם נשלח ישירות ולא דרך הממשק; כל הבדיקות האוטומטיות עוברות.
- ה-API מחזיר את מבני התשובה והקודים המוגדרים בארכיטקטורה, ללא Cache של בדיחות.
- המפתח אינו מופיע ב-Bundle של ה-Frontend, בבקשות שיוצאות מהדפדפן או בתגובות ה-API.
- נבדקה גישה ממשית ל-`gpt-5`; אם אינו זמין לחשבון, עוצרים ומציגים למשתמש את החסימה — לא מחליפים מודל על דעת עצמנו.

## Milestone 3 — Offline והפעלת PWA ✅

**שם ומטרה:** לאפשר התקנה כ-PWA ופתיחה ללא אינטרנט, ולטפל במצב ניתוק.

**דרישות מקדימות:** הקובץ `spec/assets/app-icon.png` סופק (DESIGN 1.5).

**מה יש לממש:**
- הצגת **"נדרש חיבור לאינטרנט כדי ליצור בדיחה"** בהיעדר רשת, לפי כללי הזיהוי ב-ARCHITECTURE 2.6 ומצב ה-Offline ב-DESIGN 1.4, תוך שמירה על זמינות מעטפת הממשק.
- הגדרת `vite-plugin-pwa`, Web App Manifest, אייקונים בכל הגדלים (כולל `apple-touch-icon`) שמופקים מ-`app-icon.png`, Service Worker ו-Caching של קובצי המעטפת בלבד (כולל גופנים ותמונת החתלתול). אין לשמור תשובות בדיחה במטמון או באחסון מתמשך.
- בדיקה בטלפונים אמיתיים (Chrome ב-Android וב-iPhone) על Preview ידני: התקנה, פתיחה Offline, גלילה בבדיחות ארוכות ושימור פריסת המובייל.

**תוצר מצופה:** האפליקציה ניתנת להתקנה כ-PWA ונפתחת בלי אינטרנט לאחר טעינה או התקנה מוצלחת, עם הודעה ברורה כשמנסים ליצור בדיחה בלי חיבור.

**Definition of Done:**
- לאחר שהאפליקציה נטענה ברשת ונכסי המעטפת נשמרו, ניתן לפתוח אותה ללא חיבור — עם הגופנים ותמונת החתלתול; ניסיון יצירה במצב זה מציג את הודעת ה-Offline ולא שולח בקשה.
- כשל רשת כשיש חיבור מציג את הודעת השגיאה הכללית, לא את הודעת ה-Offline.
- האפליקציה הותקנה בפועל דרך Chrome ב-Android, ונבדקה ההתקנה דרך Chrome ב-iPhone במגבלות iOS המתועדות בארכיטקטורה.
- בדיחות ונתוני נושא אינם נשמרים בין הפעלות, ותגובות `/api/joke` אינן נשמרות במטמון.
- כל המצבים נשארים באותו מסך, ללא מודאלים, תפריטים או דפים חדשים.

## Milestone 4 — בדיקות קבלה ב-Production והגנת עלויות ✅

**שם ומטרה:** לוודא שהאפליקציה המפורסמת ב-Production עובדת במלואה, מאובטחת ומוגנת מפני עלויות חריגות.

**מה יש לממש:**
- בדיקות קבלה בכתובת ה-Production בדפדפן Chrome על Android ועל iPhone, כולל RTL, יצירת בדיחה, שגיאות, התקנת PWA והתנהגות Offline.
- בדיקת כותרות האבטחה (`nosniff`, `Referrer-Policy`, CSP), תגובות ללא Cache וזמינות ה-Endpoint.
- אימות עם בעל המוצר שתקרת ההוצאה החודשית וההתראות ב-OpenAI פעילות, ושההגדרות ב-Vercel מתאימות לתוכנית שנבחרה; אין להוסיף Rate Limiting בניגוד ל-PRD.
- מילוי פקודות ההרצה והבדיקות ב-`CLAUDE.md`, אם טרם מולאו.

**תוצר מצופה:** האפליקציה זמינה לציבור ב-Vercel, נבדקה במלואה ב-Production, וניתנת לעדכון באמצעות Push ל-GitHub.

**Definition of Done:**
- כתובת Production עם HTTPS מציגה את המסך היחיד וה-API פועל באותו Origin.
- בדיקות הקבלה של Milestones 1–3 עוברות בסביבת Production, לרבות שגיאות, נושא ריק, התאמת שפה, מדיניות תוכן והחלפת בדיחה קיימת.
- אין חשיפה של `OPENAI_API_KEY` ל-Frontend, ל-Repository או לתגובות API; הסוד קיים רק ב-`.env` המקומי ובהגדרות Vercel.
- כותרות האבטחה קיימות ואינן מונעות את פעולת ה-Service Worker.
- תקרת ההוצאה החודשית ב-OpenAI מוגדרת ופעילה, ובעל המוצר מודע לכך שבהגעה אליה יצירת הבדיחות תיכשל עד החודש הבא.
- תועדו מגבלות אפשריות של Chrome ב-iPhone מבלי להבטיח זהות מלאה ל-Android.

## Development Execution Rules — הוראות מחייבות ל-AI המבצע

1. **יש לפתח את ה-Milestones אך ורק לפי הסדר המתואר במסמך.** כל שלב נשען על התוצר שעבר בדיקות בשלב שקדם לו.
2. **בסיום כל Milestone יש לעצור את הפיתוח**, להציג למשתמש מה מומש, כיצד ניתן להפעיל ולהתנסות בתוצר, ואת תוצאות הבדיקות מול **כל** סעיפי ה-Definition of Done; יש לציין במפורש כשלים, מגבלות או בדיקות שלא ניתן היה לבצע.
3. **אין להתחיל את ה-Milestone הבא בלי אישור מפורש של המשתמש**, גם אם כל הבדיקות עברו.
4. אין להוסיף פיצ'רים, לשנות מודל AI, להוסיף Database או לשנות דרישות מוצר בניגוד ל-PRD ללא אישור מפורש.
5. אם קובץ שמופיע ב"דרישות מקדימות" של Milestone חסר — יש לעצור ולבקש אותו לפני תחילת הבנייה.
